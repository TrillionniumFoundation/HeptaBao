# Search public-source semantics for the fixed worker/jobs candidate query

Public reference: TrillionniumFoundation/hepta-runtime ref e1eb14ae8eff2fc2c3565a86a36b10dd44eac915. Its jobs.rs entry is exactly the previously reviewed fc559bec715e95fee000b65c54c083f4fdd43450. These source bytes explain the reference implementation; they are not a whole-file attestation of the deployed runtime.

1. **Relative-path glob.** search_worker.py602 constructs name at the root and relative + '/' + name below it. At622 it evaluates included(path) before content reading. search_globs.rs63–76 retains patterns already containing '/' and compiles with literal_separator(true). Thus 1a1ac*/request.json is a root-relative one-directory-component file filter, not a basename-only pattern.
2. **Real directory pruning.** worker611–618 checks excluded(path, is_directory) before opening or recursing into a directory. Exclusion globs selecting the old 1a1a0* through1a1ab* directory prefixes therefore prevent their descendants from being visited. The positive file filter alone does not prune unmatched directories: selects()257–263 initializes directory selection true. Each encountered root-level entry is still counted at588–590 before exclusion. Neither pruning nor the current root count proves the search cannot reach its entry/time limit.
3. **Content match versus preview.** worker499 applies the literal matcher to the complete decoded line. It then builds a preview from the first512 UTF-8 bytes at486–502, not a window centered on the matching digest. A single-line request may therefore match a digest near its end while showing only its prefix. append()448–464 can reduce that prefix to128 bytes if the encoded row otherwise exceeds8192. Returned path and line identify a candidate; preview alone does not establish the complete request digest or a job identity. Exact fixed-file metadata and whole request binding must follow separately.
4. **File-name mode differs from content mode.** worker625–638 opens a candidate regular file, fstats it and closes it, without reading its body; it emits only regular-file paths, not directories. Content mode intentionally reads accepted regular files under the byte cap, then matches their decoded lines. The proposed content query is not a metadata-only or zero-body operation.
5. **Incomplete searches stay incomplete.** Entry/result/read/time/depth limits and unreadable/skipped records remain visible. A missing match, clipped preview, partial coverage, or this source reference never authorizes business replay or proves absence.

This handoff performed only Git reads and text inspection. It started no search or Runtime operation, and contains no other worker request bodies or stdin contents. The root's separately executed search and any subsequent exact candidate binding remain separate evidence.
