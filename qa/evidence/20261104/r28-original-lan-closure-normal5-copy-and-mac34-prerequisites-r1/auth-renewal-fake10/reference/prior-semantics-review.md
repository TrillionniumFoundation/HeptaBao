## Empty JSON and the lifetime calculation

The candidate sends exactly POST auth/token/renew-self with {} (candidate lines 827–837). auth.rs 7121–7125 permits an absent increment and retains the authenticated actor's service-token digest. After ACL/active-token checks, 7177–7178 dispatches AppRole before the separate precise Token API renewal path. auth_approle_renewal.rs 142–170 requires the stored AppRole provenance, same namespace, parentless service token, renewable flag, active mount and actual role; duration({}, increment, 0) yields zero.

For this nonperiodic route, native_token_expiry (auth_native_token.rs 23–62) uses the current role/mount default when increment is zero. It computes now + default TTL and clamps to issued_at + effective maximum and any explicit cap captured at issuance. It does not add the requested lease to the previous expiry. The actual fixture fixes role TTL180/max600 (candidate 752–754); the mount can further reduce these values. The ordinary maximum and the captured explicit maximum are distinct: AppRole issuance resets max_expires_at to the explicit cap, which is absent by default (auth.rs 9007–9053). A lookup explicit_max_ttl of zero therefore does not remove the ordinary600-second bound.

Renewable=true is a flag, not proof of unused maximum headroom. A live token already at its maximum absolute expiry can return200 and a smaller positive lease duration without extending expiry. At expiry, active-token admission rejects it; if an administrator lowers a still-live role's maximum below the elapsed age, the backend can instead return500 past the max TTL. The existing product test source auth_approle_renewal_tests.rs108–183 covers missing/zero increment and these changed-role/error distinctions; those tests were not run here. Empty renewal can also reduce a previously longer grant when the live default is shorter. The candidate's increasing/unchanged/decreasing labels correctly avoid assigning a cause solely from the sign.

## Receipt fields, precision, and same credential

AppRole login uses login_token with token_api_precision=None and u64 created_at/expires_at (auth.rs9036–9053,9185–9217). Its renewal updates that same u64 field. Its lookup returns integer ttl=expiry.saturating_sub(now), expire_time_unix=expiry, creation_time, renewable, type and namespace (9249–9256). AuthorityTime.seconds uses the integer second component even for a precise request clock (auth_token_precision.rs301–325). There is no fractional timestamp parsing in this candidate, and no float/timezone conversion of expire_time. The separate Token API precise lookup path at auth.rs9224–9243 has different rounding; it is not this AppRole issuance route and should not inherit this fixture's qualification.

The current HTTP owner explicitly echoes the presented credential into renew auth.client_token and lookup data.id (service_native_auth.rs2539–2569). Thus the candidate's required fields are actually present. This echo alone is not independent authentication proof: the product first authenticates the actor and resolves the stored token; the candidate also binds accessor and creation_time across the two lookups and accessor in the renewal response. It keeps raw identity values private and exports only the fixed lifetime fields and equality booleans. Initial and cold phases independently capture their respective token; no cross-generation token equality is presumed.

The post lookup, rather than the renew response's lease_duration, is the decisive expiry observation. TTL need not increase, because time passes between requests. For this coarse AppRole route, a positive stored expiry difference is not a subsecond rounding artifact. An unchanged expiry may be correct in the same integer second or at the cap. Moving the pre lookup before the existing KV/ACL operations improves the chance of elapsed time but cannot guarantee a second boundary. It also cannot guarantee the token remains live through arbitrarily slow allowed requests. Neither uncertainty justifies sleep, retry, refreshed credentials, changed limits, or a synthetic PASS.

## Revoke, final qualification, and failure boundaries

The candidate still checks unassigned403, renew200, post lookup200, revoke-self204 and revoked-resource403, in that order (827–852). revoke-self uses the authenticated digest and returns empty(mutated=true), whose HTTP status is204 (auth.rs7059–7064,1910–1921); revoke removes the token and descendants (3453–3474). The delta is returned only after both revoke observations. A valid unchanged/decreasing expiry therefore does not skip this original chain. The new both-expiries-increased requirement is evaluated after both inverse phases and the original final validation (candidate1087–1099).

If a response, validator, deadline, or socket closure fails after dispatch, the original LoopbackHTTP423–505 conservatively records unknown and forbids later requests. The same-second known evidence-gap interpretation is conditional on the whole original chain and owned closure being known; it does not overwrite any independent unknown or pretend that an early failure completed revoke/inverse. The600-second lifetime checks are tied to this fixture's frozen role and must not be copied as a generic production/periodic-token rule.
