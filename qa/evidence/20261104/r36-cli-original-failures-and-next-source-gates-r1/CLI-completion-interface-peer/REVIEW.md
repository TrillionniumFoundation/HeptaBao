# Binary snapshot forwarding — narrow completion / delivery interface review

Scope: source advice only. Two exact current source blobs were fetched whole and the completion digest/seal and delivery/Actor/audit paths were read. No new binary implementation is assessed or approved; no Runtime, SDK, Rust or product test ran.

## Concrete integration requirements

1. **A binary attachment is absent from the current response digest.** completion lines194–253 hash the status, JSON body, response headers and typed unwrap origin. A new typed binary descriptor must feed both local response_digest and wire_response_digest with the same domain-separated representation, including payload kind, exact length/hash, status and the permitted canonical headers. It must ultimately be authenticated by publication_bytes (lines760–809). Adding an un-MACed wire field, or attaching a pathname/FD beside the old JSON receipt, does not bind the archive. Keep ordinary JSON encodings byte-identical.

2. **Preserve affine receipt construction and the separate MAC verification.** CompletedForwardReceipt has no Clone and is constructed only by the authenticated exchange (lines75–150). verified checks the actual nonce, serialized request digest, response digest, original deadline, audit fields, prefix/index and owner projection. verify_publication is called later by sync_completed_forward_receipt before interpreting the prefix (delivery lines287–318). A new deserializable descriptor must not itself manufacture the affine delivery authority. The response kind and negotiated protocol must be validated before selecting a binary completion branch.

3. **Do not borrow unrelated exceptions to bypass the snapshot Actor.** completion lines633–653 permit an acknowledgement-only 204/null response to take a special Actor path; delivery lines486–501 skips Actor validation for acknowledgement_only. Snapshot restore must not become acknowledgement-only just because its eventual success is 204. Snapshot save/restore need the actual route's admitted Actor and original clock. Similarly, NativeDataReadPublication is a KV2 retained-read scope (completion119–131,319–365 and719–734; delivery395–425), not a generic historical snapshot proof. If a snapshot needs a distinct retained-publication exception, that contract must independently bind its exact retained root/content and stable owners.

4. **The existing audit gates precede delivery; streaming cannot undo bytes already sent.** delivery508–572 rechecks the same response digest, original authority and original deadline both before and after local mandatory audit. A new binary capability must be held until those gates pass, and cleared/dropped on PendingForwardDelivery::Rejected, pre-audit failure and post-audit veto. Current erase_json, unwrapped_json=None and header clearing do not by themselves revoke a new FD or streaming object. Show the output-emitter ownership path that prevents the first client body byte from preceding final delivery admission. Do not turn a partial binary response into a fabricated successful JSON response or an automatic replay.

5. **Actual upload completion must precede publication of its proof.** delivery574–699 explicitly seals while the original Service writer is still held, after original route audit/final gates, with a fresh application witness, current owner projection and terminal Actor check. completion669–748 only completes within the original clock/deadline and consumes captured Actor state. For streamed restore, a header-only request digest is insufficient: the actual byte count, whole hash and terminal EOF/end-of-upload event must be bound to the same authenticated request/nonce before the restore publication/completion can be sealed. A later sidecar hash cannot retroactively authenticate an already published mutation. Preserve the original writer and time owner rather than reacquiring or minting a new Actor.

6. **Maintain current catch-up and failure semantics.** stage_forward_delivery captures local seal/barrier/namespace custody only after legitimate catch-up (delivery217–246). The subsequent local synchronization may continue only its existing Superseded path and never executes the original remote request or consumes Actor use again (248–354). A committed restore followed by missing completion or audit/delivery veto remains a potentially durable outcome requiring reconciliation. It must not be relabeled “no effect” or retried under another key. The existing forward_delivery_veto audit failure fences the service and sets recovery_required (553–568); a binary extension must preserve that behavior and release its own resources.

7. **Headers are part of the proof, not an arbitrary late mutation.** completion561–619 presently recognizes only the bounded quota-header merge for its narrow acknowledgement/denial cases. Binary Content-Type/Content-Length or other permitted headers need an explicit canonical, identical local/wire descriptor projection; do not use the quota allowance to insert unbound binary semantics. Any post-seal mutation must continue to fail response_matches.

## Limitations

This review does not inspect a proposed new descriptor implementation, transport framing, endpoint authentication, snapshot spool owner, upload/download emitter, or raw HTTP behavior. The exact caller wiring is therefore still required. It gives current source integration constraints, not a runtime qualification or a claim that the source-only architecture already satisfies them.
